# Дослідження GIL та паралелізму

## Чому потоки під GIL не прискорили індексацію?
Global Interpreter Lock (GIL) — це механізм у CPython, який дозволяє виконувати байткод Python лише одному потоку в один момент часу. Побудова інвертованого індексу (токенізація, підрахунок частот, створення словників) є задачею, обмеженою процесором (CPU-bound). Тому, хоча `ThreadPoolExecutor` і створює кілька потоків, вони змушені постійно чекати один одного, поки звільниться GIL. У результаті використання потоків не дало жодного прискорення (час виконання залишився на рівні serial-версії), а іноді навіть зріс через накладні витрати на перемикання контексту між потоками.

## Чому процеси прискорили і чим це оплачено?
`ProcessPoolExecutor` створює окремі процеси операційної системи. Кожен процес має свій власний інтерпретатор Python і, відповідно, свій власний GIL. Це дозволяє їм виконувати код по-справжньому паралельно на різних ядрах процесора. 
**Ціна цього:**
1. **CPU time проти Wall time:** Загальний час (Wall time) зменшився (прискорення до 1.6x), але сумарний час процесора (CPU time) залишився високим, оскільки кілька ядер працювали одночасно.
2. **Накладні витрати (Overhead):** На Windows (через метод `spawn`) створення кожного нового процесу займає багато часу. Це видно з результатів: `processes` не показали лінійного прискорення (наприклад, 8x на 8 ядрах), бо значну частину часу витрачають саме на запуск.
3. **Pickle:** Передача даних між процесами вимагає серіалізації. Ми передаємо лише шляхи до файлів, що дешево, але повернення списків токенів все одно вимагає ресурсів.
4. **Пам'ять (RSS):** Кожен процес споживає додаткову пам'ять. У наших вимірах RSS батьківського процесу коливається, оскільки дочірні процеси мають власну пам'ять.

## Де в часі видно закон Амдала?
Закон Амдала говорить, що прискорення обмежене тією частиною програми, яку неможливо розпаралелити. У нашій архітектурі функція `merge` (злиття часткових індексів) виконується в головному процесі послідовно. У таблиці бенчмарку видно, що час `Merge (s)` становить близько 1.1–1.2 секунди і **майже не змінюється** залежно від кількості воркерів. Навіть якщо ми матимемо нескінченну кількість ядер для `build_partial`, час на `merge` не зменшиться. Це створює "стелю" для максимального прискорення, яку добре видно на графіку `docs/speedup.png` — лінія не досягає ідеальної прямої.

## Що змінилось на 3.13t (без GIL)?
У збірці Python 3.13t (free-threaded) GIL вимкнено (перевірка `sys._is_gil_enabled()` повертає `False`). 
Виявилося, що для нашої задачі потоки все одно не дали значного прискорення (Speedup ~1.0x). Це пояснюється тим, що:
1. Передача великих об'єктів (списків токенів) між потоками все одно вимагає синхронізації або створює велике навантаження на пам'ять.
2. Задача побудови індексу має багато дрібних операцій з пам'яттю, які в 3.13t можуть блокуватися на рівні структур даних (наприклад, внутрішні блокування словників).
3. Накладні витрати на створення потоків "з'їдають" виграш.

Висновок: навіть без GIL паралелізм потоків не є "срібною кулею" для будь-якої CPU-задачі, і архітектура передачі даних (pickle) відіграє величезну роль. Крім того, в 3.13t з'являється небезпека при спільному доступі до пам'яті без `threading.Lock`, чого не було при GIL.
