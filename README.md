# Лабораторна робота 2 - інвертований індекс, пошук та серіалізація

## Опис та репозиторій
* **репозиторій:** Публічний GitHub-репозиторій проєкту (тег `lab-02`).
* **Мета роботи:** Побудова пам'ятно-оптимізованого інвертованого індексу, реалізація ефективних алгоритмів булевого пошуку (`AND`, `OR`, `NOT`), серіалізація та бенчмаркінг продуктивності.

## Структура проєкту

## Бенчмарк: Merge vs Set (Час виконання)

Порівняння швидкодії пошукових алгоритмів для булевих операцій (`AND`, `OR`) на тестовому корпусі:

| Операція / Запит | Алгоритм `merge` (сек) | Алгоритм `set` (сек) | Примітка |
|---|---|---|---|
| `python AND async` | 0.0012 | 0.0009 | `set` швидше завдяки оптимізованим хеш-таблицям Python |
| `database OR sql` | 0.0018 | 0.0014 | `merge` ефективний на відсортованих Posting-писах |
| **Середній час** | **0.0015** | **0.0011** | **Множини (`set`) демонструють менші накладні витрати** |

# Лабораторна робота 3

## Структура проєкту
* `src/findex/index.py` – об'єктно-орієнтований клас `Index` (наслідує `Mapping`), кешування властивостей (`@cached_property`) та контекстний менеджер `open_index`
* `src/findex/search.py` – алгоритми ранжування `TfIdf` та `BM25`, синтаксичне дерево (AST) для булевих запитів із перевантаженими операторами та рекурсивний спуск (`QueryParser`)
* `src/findex/cli.py` – розширений інтерфейс для ранжованого та булевого пошуку з кешуванням і заміром часу

## Особливості реалізації та оптимізації
* **Протокол ранжування**: використання датакласу `SearchResult` з підтримкою сортування (`order=True`) та `heapq.nlargest` для швидкого знаходження топ-$k$ документів.
* **Декоратори**: `@timed` (через `functools.wraps`) для моніторингу часу виконання та `@lru_cache` для кешування результатів пошукових запитів.
* **Генерація сніпетів**: автоматичне створення контекстного вікна ($\pm 80$ символів) навколо знайденого терміна.

## Санітарні перевірки ранжування (Sanity Checks)
1. **Рідкісний термін вище частого**: Запит за специфічним терміном (`"asyncio"`) повертає вищий бал для документів, де він є унікальним, ніж загальні стоп-слова.
2. **Насиченість частоти (Term Frequency Saturation)**: 20-те повторення терміна в одному документі майже не збільшує його загальний бал (параметр $k_1=1.5$).
3. **Штраф за довжину документа (Document Length Penalty)**: Короткий документ із єдиним входженням терміна отримує вищий ранг, ніж довга стаття (коефіцієнт $b=0.75$).

# Лабораторна робота 4


## Структура проєкту

* `src/findex/` — анотований вихідний код проєкту зі строгим режимом перевірки типів (`pyright strict = 0 errors`).
* `src/findex/search.py` — алгоритми ранжування через `Protocol` без наслідування, токенізатор та парсер синтаксичного дерева.
* `src/findex/cli.py` — консольний інтерфейс на `typer` з підкомандами `index`, `search`, `stats` та обробкою логування у `stderr`.
* `tests/` — тестове покриття на `pytest` (>30 тестів) та перевірка інваріантів за допомогою `Hypothesis`.

## Особливості реалізації та типізації

* **Протокол скорера**: Інтерфейс `Scorer` реалізовано як `typing.Protocol`, що дозволяє `pyright` перевіряти обидві реалізації (`TfIdf` та `BM25`) без явного наслідування.
* **Сувора типізація**: Параметри на кшталт `engine` і `scorer` обмежені через `Literal`, а генератори анотовані як `Iterator` чи `Iterable`. Усі `# type: ignore` мають пояснювальні коментарі.
* **Обробка діагностики**: Усі діагностичні повідомлення спрямовуються в `stderr`. Логер налаштовується один раз у точці входу CLI.

## Інсталяція та запуск CLI

### Властивості Hypothesis:

1. **Збереження та завантаження**: $load(save(index)) \equiv index$.

3. **Еквівалентність merge**: Операція $merge$ збігається з відповідними операціями над множинами ($set$).
