# лабораторна робота 1 - проєкт findex

## опис проєкту
мета роботи — реалізація ітераторів, генераторів, потокового токенізатора з нормалізацією Unicode та порівняння споживання пам'яті між лінивим підходом і «жадібним» за допомогою бібліотеки `tracemalloc`

## структура проєкту
- `src/indexer.py` — генератори для читання документів, потоковий токенізатор та збір статистики
- `src/greedy.py` — жадібна версія реалізації на списках для порівняння
- `tests/test_tokenizer.py` — модульні тести для токенізатора
- `data/` — корпус текстових файлів

## результати вимірювань та бенчмарку
вимірювання проводились на корпусі з 5 документів (загалом 609 317 токенів)

### генератори (лінивий підхід)
- час виконання: 1.01 сек
- пікове споживання пам'яті: 30.32 МБ
- висновок: пам'ять витрачається ефективніше, оскільки файли та токени обробляються по черзі потоком без масового накопичення всіх даних в одному списку

### списки (жадібний підхід)
- час виконання: 0.74 сек
- пікове споживання пам'яті: 39.71 МБ
- висновок: споживання оперативної пам'яті вище через одночасне збереження повного вмісту всіх файлів та всіх токенів у структурах типу `list`

# Лабораторна робота 2 - інвертований індекс, пошук та серіалізація

## Опис та репозиторій
* **репозиторій:** Публічний GitHub-репозиторій проєкту (тег `lab-02`).
* **Мета роботи:** Побудова пам'ятно-оптимізованого інвертованого індексу, реалізація ефективних алгоритмів булевого пошуку (`AND`, `OR`, `NOT`), серіалізація та бенчмаркінг продуктивності.

## Структура проєкту
* `src/indexer.py` – потоковий читач документів та токенізатор.
* `src/models.py` – пам'ятно-оптимізовані класи `Posting` та `DocMeta` з використанням `@dataclass(frozen=True, slots=True)`.
* `src/inverted.py` – побудова інвертованого індексу та його серіалізація/десеріалізація через `pickle`.
* `src/search.py` – реалізація Boolean-пошуку (двовказівниковий алгоритм `merge` проти операцій із множинами `set`).
* `src/cli.py` – консольний інтерфейс для побудови, збереження, завантаження та пошуку.

---

## Бенчмарк: Merge vs Set (Час виконання)

Порівняння швидкодії пошукових алгоритмів для булевих операцій (`AND`, `OR`) на тестовому корпусі:

| Операція / Запит | Алгоритм `merge` (сек) | Алгоритм `set` (сек) | Примітка |
|---|---|---|---|
| `python AND async` | 0.0012 | 0.0009 | `set` швидше завдяки оптимізованим хеш-таблицям Python |
| `database OR sql` | 0.0018 | 0.0014 | `merge` ефективний на відсортованих Posting-писах |
| **Середній час** | **0.0015** | **0.0011** | **Множини (`set`) демонструють менші накладні витрати** |


## Споживання пам'яті та показники Save / Load

### 1. Таблиця споживання пам'яті структурами даних
| Об'єкт / Структура | Оптимізація (`slots=True`) | Розмір / Кількість |
|---|---|---|
| `DocMeta` (метадані документа) | Так | ~48 байт / об'єкт |
| `Posting` (ідентифікатор + частота) | Так | ~32 байт / об'єкт |
| Словник індексу (`dict`) | Базовий | Залежить від кількості унікальних термінів |

### 2. Час збереження та завантаження індексу (Save / Load)
* **Час серіалізації (`save` через `pickle`)**: ~0.35 сек (для корпусу ~500К+ токенів).
* **Час десеріалізації (`load`)**: ~0.18 сек (швидке завантаження готового бінарного файлу індексу в пам'ять).
